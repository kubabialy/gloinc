# Million-record stress driver

`main.gloin` replaces `scripts/check-integrated-examples.py`. Build with
`cmake --build build --target gloin_stress_tests`, then run:

```sh
build/gloin-stress-test build/gloinc examples build
```

Arguments are the compiler, examples directory and existing temporary parent.
The driver canonicalizes these paths and creates a private unique directory.
Inputs are written in reusable blocks of 1,024 records, using bounded storage.
Every compiler invocation runs the example through JIT, with a 2 MiB child soft
stack limit, separate output pipes, its own process group and a 60-second
communication deadline. Launch/cleanup can outlast that budget; see the
[process contract](../../docs/child-processes.md#child-stack-limits).
Captured streams are limited to 256 KiB each. This is a correctness and stack
check, not a benchmark or a claim about compiler heap consumption.

The five child runs check:

- Exactly 1,000,000 configuration lines retain `label=retained`, seed 42 and
  1,000,000 samples. One extra comment produces exit 2 and only stderr.
- Exactly 1,000,000 `row,-2,4` statistics records produce the exact fixed CSV.
  One extra record produces exit 2 and only stderr, without creating its output.
- Seed 42 and 1,000,000 simulation samples produce the fixed reference below.
  The only variable field is `elapsed_ns`: nonempty ASCII decimal digits
  followed by exactly one newline.

Successful children must emit no stderr. Successful runs remove the private
tree; failures print its path and retain available captures and fixtures.
Cleanup assumes a stable owned tree and follows no final symlinks. Groups
cover ordinary descendants; detached descendants remain outside that scope.

CTest runs `GloinIntegratedStress.MillionRecords` as part of `check-core`.
Package acceptance compiles this driver with each installed/relocated compiler
and runs that package's examples. The driver itself is a repository test tool,
not an installed executable.

## Independent reference provenance

The expected values were frozen from the retired script's independent
exact-integer implementation, then verified by running both drivers before
removing the script. They are not generated by `@random` or by the simulation.
The algorithm is specified here so the fixture remains independently reviewable:

1. Set `state = 42`. Each draw adds `0x9E3779B97F4A7C15` modulo `2^64`.
2. Copy state to `word`. Replace word with
   `(word XOR (word >> 30)) * 0xBF58476D1CE4E5B9` modulo `2^64`, then
   `(word XOR (word >> 27)) * 0x94D049BB133111EB` modulo `2^64`.
   Return `word XOR (word >> 31)`.
3. Per sample draw `x = draw() >> 11` and `y = draw() >> 11`.
   Count the point inside when the **exact integer** comparison
   `x*x + y*y <= 2^106` holds.
4. Draw a die word, retrying while `word < 4` (`2^64 modulo 6`).
   Add `word modulo 6 + 1` to the dice sum.
5. Repeat steps 3–4 exactly 1,000,000 times without resetting state.

| Field | Expected |
| --- | --- |
| `inside` | `785115` |
| `dice_sum` | `3503215` |
| `pi` | `3.140460` |
| `abs_error` | `0.001133` |

`pi` is `4 * inside / samples` formatted to six decimals. `abs_error` is its
absolute difference from pi, also to six decimals. Neither floating-point
calculation is used to decide whether a point is inside the reference circle.
The fixed output expectation also checks field names, ordering and newlines.

Do not regenerate these values from production output. A new seed/algorithm
requires an independently reviewed reference calculation. A direct port to
Gloin's checked `u64` would not preserve wrapping multiplication; using `f64`
for the circle test would not preserve exact 107-bit arithmetic. The frozen
fixture deliberately avoids both substitutions.
